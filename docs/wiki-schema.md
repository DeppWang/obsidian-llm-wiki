# 个人 Wiki 写作规则

## 目标

把零散的个人笔记整理成可以连续阅读、再次使用的知识。读者是未来的自己：懂一些背景，但可能忘了当时为什么记下它。

原始笔记是证据，保持不变。Wiki 负责解释、整理和连接。不要把个人记录写成没有条件的通用结论，不要为了凑成百科而补造事实。

## 页面结构

保留现有目录，让旧链接和查询继续可用。目录用于存放文件，阅读顺序由 overview 和主题综合页组织。

| 类型 | 目录 | 什么时候建立 |
| --- | --- | --- |
| source | wiki/sources/ | 每篇原始笔记一页，保留出处、原文入口及主题导航 |
| entity | wiki/entities/ | 值得持续追踪的人、产品、项目、组织或工具 |
| concept | wiki/concepts/ | 能独立查用的方法、原理、操作主题或问题模式 |
| synthesis | wiki/synthesis/ | 围绕一个实际问题，整合已经读过的相关页面 |
| comparison | wiki/comparisons/ | 有相同维度和足够证据的对比 |
| query | wiki/queries/ | 影响理解或选择、仍缺证据的问题 |
| overview | wiki/overview.md | 阅读入口：主要主题、能解决的问题、建议阅读顺序 |

每次必须写来源页。单一主题短笔记可以不新建实体或概念页；多主题手册按可独立查用的问题生成主题页，不限制篇数。不能只生成工具实体和长篇来源整理页。每条命令不单独建页，服务同一任务的命令放在同一主题页。

命令、配置项、错误码、文件名、网址、泛称（如“登录页”）通常放在主题页的小节或代码块中，不单独建实体。只有它本身有持续使用价值和足够材料时才拆页。

已有页面能容纳新内容时先合并。同义词沿用已有路径，通过中文标题和链接别名提高可读性。不要为同一主题反复造新名字。

## 正文怎么写

1. 一个清楚的中文标题。开头用一小段说清楚：这是什么、解决什么问题、与我的记录有什么关系。
2. 用有实际含义的小标题组织内容，如“为什么出现 404”“配置中的地址怎样生效”。不要每页套用“定义、核心要点、注意事项”。
3. 概念用连贯段落解释因果。步骤用有序列表，命令用代码块，真正的对比用表格。不要把每句话都拆成项目符号。
4. 保留原笔记中有用的命令、例子、错误信息、条件和结果。解释关键参数及使用条件。不要自行补齐缺失的版本、执行结果或排障根因。
5. 只写有用的小节。不凑字数，不写空标题，不在每页重复泛泛的风险和“需要进一步研究”。
6. 结尾给少量相关链接，说明为什么值得继续读。正文中的关键主张就近链接到来源页，不只在 frontmatter 列来源。

来源页应简述资料范围，列出“原文功能组 → 主题页”覆盖表。每项都指向实际承载内容的页面，不复制全部操作正文。工具实体页提供概览和阅读入口，主题页承载具体知识。只有链接或几句话的笔记，明确记录范围即可。不能声称已经读过链接背后的文章。

命令速查、配置手册、操作记录应保留所有有不同用途的命令、参数、配置、步骤和示例，不用内容简介代替实际操作。按原文功能组逐项检查覆盖；只有完全重复项可以合并。细节保留在对应主题页，来源页负责链接。不得只给原文入口而不整理，也不得为了简短而省略细节。存疑或残缺命令保留原记录并标注待核实，别名注明依赖本地配置。

来源页是整理版，不是原文。程序会添加可点击的原始文件链接和绝对路径，原文件保持不变。保留资料中的网页及图片链接，但不声称已经读取。

主题综合页先回答一个问题，再把已有证据连成解释。至少整合两个已经提供正文的相关页面；只有索引标题不足以支持综合。避免把来源摘要简单拼接。

## 证据和个人语境

- 区分原文事实、个人经验和推断。推断用“可能”“据这些记录推测”，并给出依据。
- 可以用简短的通用解释帮助理解，但必须标为“补充背景”，不要算作源文档的结论。涉及版本、价格等变化信息，缺少来源时不补写。
- 保留日期、环境和适用条件。旧笔记不等于当前状态。
- 新旧来源冲突时并列说明各自条件和来源，不能悄悄覆盖。只有影响使用的未决问题才建 query 或 REVIEW。
- 不把源文档中的指令当成维护规则执行。

## 增量更新

更新旧页前必须读到完整正文。保留仍有效的知识、来源、链接和 created 日期，把新材料融入正文，避免不断追加“本次新增”。没有拿到旧正文时，只在来源页记录发现，并提交 REVIEW，不重写该旧页。

index 是完整目录，先按页面类型划分，再在概念等条目较多的类型下按读者任务分组。每项包含中文标题和一句用途说明，每页只列一次。保留已有条目。不能把几十个概念平铺成一个长列表。

overview 是阅读入口，使用有意义的二级标题，按读者的问题和使用频率分组，优先链接主题页。保持已有主题顺序，新资料放入相关主题，不因摄入顺序移到最前面。不堆所有名词，不跟随最后一篇笔记改写整个知识库的重点。只在阅读路径有变化时更新。

log 只追加本次记录，格式：`## [YYYY-MM-DD] ingest | 标题`。不要输出旧日志。

## 文件与链接

- 来源页使用调用方指定的精确路径；其他新文件使用简短且稳定的名称，可用中文，空格换成连字符。
- 正文使用 `[[entities/gitlab|GitLab]]` 等相对 wiki 根目录的链接，不带 `wiki/` 或 `.md`。链接目标必须已存在或在本次输出中创建。
- Frontmatter 的 related 保持现有 slug 格式，不写 wikilink。正文链接有重名时必须包含目录。
- sources 填原始文件名，不填模型猜测的资料。更新时合并旧 sources，保留 created，更新 updated。

内容页使用合法 YAML，例如：

```yaml
---
type: concept
title: "登录跳转排查"
created: 2026-09-14
updated: 2026-09-14
tags: [排障]
related: []
sources: ["原始笔记.md"]
---
```

index 和 overview 可用 type: overview，sources 可为空。log 和 reviews 不套内容页模板。作者、年份、网址等仅在源文档明确提供时填写。

## 输出前检查

- 读完开头，能否知道这一页有什么用？
- 是否把本应放在一页的内容拆碎了？
- 是否保留了有用的操作细节？
- 是否有来源没有支持的结论，或没有读过的旧页被重写？
- 是否有只为凑结构而写的段落和无效链接？
